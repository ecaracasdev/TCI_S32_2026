# Changelog

Registro de cambios relevantes del proyecto. Formato basado en [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/).

## [Unreleased]

### Security

- `SECRET_KEY` y `CLAVE_JWT` ya no están en `config.toml` (traía `SECRET_KEY = "123456"` y `CLAVE_JWT` vacía). Se leen de las variables `AUTOCONFIG_SECRETS__SECRET_KEY` y `AUTOCONFIG_SECRETS__CLAVE_JWT`; `docker compose` las toma de un `.env` que no se versiona (issue #92, M6). `SECRET_KEY` es obligatoria y exige 32 bytes; si falta o es corta, el backend aborta con un mensaje que explica cómo definirla. Verificado con `docker compose`: el backend arranca con las claves, `POST /auth/token` responde `400` (login activo) y la API sin token responde `401`; sin las claves, la imagen termina con código `1` y el mensaje. `CLAVE_JWT` ya exigía 32/48/64 bytes según el algoritmo, pero no tenía tests: ahora se prueba el límite exacto.

### Changed

- Numeración de los casos de uso por integrante: CUN-01 y CUN-02 (Elias), CUN-03 (Martin, `docs/caso-de-uso-cun03-aprobar-pedido.md`) y CUN-04 (Nicolás). "Registrar un repuesto" pasa de CUN-02 a **CUN-04** (`docs/negocio/casos-de-uso/cun-04-registrar-repuesto.md`) para no chocar con "Cargar stock recibido con ubicación", que queda como CUN-02.
- `docker compose up` requiere un `.env` con `SECRET_KEY` y `CLAVE_JWT` (copiar `.env.example`). El compose activa el JWT local con `AUTOCONFIG_AUTH__JWT__HABILITADO=true`; `config.toml` ya no define `HABILITADO` (el valor por defecto sigue siendo `false`) porque el archivo gana sobre la variable.

### Fixed

- Las variables de entorno `AUTOCONFIG_*` nunca funcionaron: se leían en minúsculas y los campos de la configuración están en mayúsculas, así que el modelo las rechazaba y definir cualquiera hacía fallar la carga de toda la configuración. Ahora se resuelven al nombre real del campo, sin distinguir mayúsculas.

### Added

- CUN-01 de punta a punta (issue #112): el empleado toma una incidencia reportada o en triage (`POST /api/v0/incidencias/{id}/reparacion`, nueva operación del contrato v0), registra los repuestos usados (`POST /api/v0/reparaciones/{id}/usos`, RN-01) y la resuelve con el informe (`POST /api/v0/reparaciones/{id}/informe`); `GET /api/v0/reparaciones/{id}` devuelve usos e informe, y el detalle de la incidencia suma `reparacion_id`. El uso valida contra el disponible (no usa lo reservado), descuenta con una sentencia condicionada (`docs/M6-adr-concurrencia-rn01.md`) y deja un movimiento `consumo`. En el front: tomar, registrar uso (pantalla de T17 conectada) y finalizar desde el detalle de la incidencia, solo para el empleado. Tests de RN-01 y del flujo, verificados rompiendo cada regla; recorrido completo probado en el navegador contra PostgreSQL.
- `docs/demo/levantar.md` (levantar el sistema, cargar los datos de prueba, usuarios por rol, acceso a la base, tests y problemas comunes) y `docs/demo/guion.md` (guion de la demo con el reporte de incidencias del operario, catálogo, stock, reservas y permisos), enlazados desde el README. Recorridos desde un clon limpio del repositorio.
- Incidencias visibles en el frontend según el rol acordado: solo el operario ve y usa "Reportar incidencia"; todos los roles ven "Incidencias" (listado y detalle) y la tarjeta "Incidencias recientes" en inicio. El backend deja reportar solo al operario (antes también al encargado) y el listado devuelve primero las más recientes. Tests de la matriz de permisos y del orden. Verificado en el navegador con operario, empleado y gerencia contra el backend real.
- Frontend: el menú muestra a cada rol solo los módulos que el backend le permite (`docs/actores.md`) y un guard por rol devuelve a inicio a quien escribe a mano una ruta sin permiso; gerencia no entra a crear ni editar repuestos. Se ocultan del menú y de las rutas las pantallas cuyo backend todavía no existe (incidencias, registrar uso, pedidos de compra y la vista de componentes); "Repuestos por reponer" en inicio se calcula con los repuestos reales hasta que exista `/stock/alertas`, y se quita "Generar orden de compra", que no guardaba nada. Verificado en el navegador con los 4 roles.
- `docker compose` levanta PostgreSQL 16 (servicio `db`, volumen `pgdata`, healthcheck) y el backend se conecta con `asyncpg` usando `backend/config.docker.toml`; la contraseña llega desde `POSTGRES_PASSWORD` del `.env`. Sin Docker y en los tests se mantiene SQLite. Un test verifica que `config.docker.toml` solo difiera de `config.toml` en `[database]`. Verificado en Docker: login, máquinas, repuestos, ubicaciones y reservas (crear, rechazo por stock, liberar y ejecutar, incluido un fallo que no deja cambios) contra PostgreSQL, y los datos se conservan tras `down` y `up` (issue #94).
- Endpoints de reservas del contrato v0 (`GET/POST /api/v0/reservas`, `GET /api/v0/reservas/{id}`, `POST /api/v0/reservas/{id}/liberacion` y `POST /api/v0/reservas/{id}/ejecucion`) según la máquina de estados de Reserva (T02): una reserva nace `activa` y termina `ejecutada` o `liberada`. Crear aparta stock solo si el disponible alcanza para todas las partidas; liberar exige rol encargado (RN-05); ejecutar descuenta lo consumido del stock físico y libera el resto en la misma transacción (RN-10). Cada cambio de existencias es una sentencia condicionada en la base y queda como movimiento de stock (issue #107). El estado inicial de `reservas` pasa de `planificada` a `activa` para coincidir con la máquina de estados.
- `docker-compose.yml` en la raíz, con `Dockerfile` para `backend/` (Python 3.14 + uv) y `frontend/` (build de Angular servido con nginx). `docker compose up --build` levanta todo el stack desde un clone limpio (issue #29, M2). Verificado de punta a punta: backend responde `200` en `/health`, frontend responde `200` en `http://localhost:8080`.
- `.dockerignore` en `backend/` y `frontend/` para no copiar `node_modules`, `.venv`, `dist` ni logs al build.
- Sección "Cómo levantar el proyecto con Docker" en el README principal, más una sección de Docker en `backend/README.md` y `frontend/README.md`.
- `docs/M6-adr-sqlite-o-postgres.md`: ADR de la base de datos del entregable: PostgreSQL en Docker Compose y SQLite sin Docker y en los tests (issue #94, M6). Verificado contra PostgreSQL 16: la misma carga de datos y 31 pedidos HTTP a un backend sobre cada motor dieron 29 respuestas idénticas; las 2 diferencias (búsqueda de repuestos con mayúsculas acentuadas) y lo que no se verificó figuran en el documento.
- Gestión de pedidos de compra (CUN-03): se agrega la consulta de pedidos, asignación de responsables, revisión, aprobación y cancelación con motivo. Se validan los permisos según el rol y las transiciones de estado. Se incorporan pruebas automatizadas para los casos correctos y los errores esperados.
